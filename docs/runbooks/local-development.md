# Local Development Troubleshooting

## Frontend shows "Catalog unavailable"

Check in order:

```bash
curl -i http://localhost:8080/api/health/live
curl -i http://localhost:8080/api/health/ready
docker compose logs --tail=100 backend postgres
```

- Liveness connection failure: API is not listening or the port is occupied.
- Liveness 200 and readiness 503 with `Database is unavailable`: inspect PostgreSQL health and `DATABASE_URL`.
- Readiness 503 with `Database schema is not ready`: run `make migrate-up`.
- Readiness 200 and products 500: use the response `X-Request-ID` to correlate the sanitized backend JSON log.

Do not paste credentials, tokens, headers, cookies, personal data, or raw checkout bodies into an issue or incident report.

## Register or login returns `403 origin_not_allowed`

Browser authentication mutations require an exact origin match. Use the same public URL configured in `PUBLIC_ORIGIN`:

```bash
curl --fail-with-body \
  -X POST http://localhost:3000/api/auth/login \
  -H 'Origin: http://localhost:3000' \
  -H 'Content-Type: application/json' \
  --data '{"email":"learner@example.com","password":"correct horse battery staple"}'
```

Do not use `http://127.0.0.1:3000` when `PUBLIC_ORIGIN` is `http://localhost:3000`; origins are intentionally exact. In production, set `PUBLIC_ORIGIN=https://<shop-host>` and `SESSION_COOKIE_SECURE=true`.

## Cart returns `401`, `403`, or `409`

- `401 authentication_required`: sign in at the same origin before opening `/cart`. Go authenticates before any Cart query, so this response does not expose cart contents.
- `403 origin_not_allowed`: the mutation Origin must equal `PUBLIC_ORIGIN` exactly.
- `403 csrf_invalid`: obtain a fresh token from authenticated `GET /api/auth/csrf` and pass it as `X-CSRF-Token`. This token is bound to the current session and is not the session cookie.
- `409 sku_unavailable`: the SKU is missing or not VND. Old USD demo rows remain readable in Catalog but cannot enter Cart.
- `409 cart_limit`: no more than 99 units per SKU or 100 distinct SKUs.

If the cart page fails after a schema change, check `make migrate-status`; Cart needs migration `00004`. The `price_cents` to `price_minor` rename in `00003` is an incompatible learning-repo cutover, so do not run an old API image against the new schema.

## Login succeeds but the header still shows “Sign in”

Check the same-origin proxy and cookie path without copying the cookie value into logs:

```bash
docker compose logs --tail=100 frontend backend
curl -i http://localhost:3000/api/me
```

An unauthenticated `curl` should receive `401`; that is expected because it has no browser cookie. In browser developer tools, inspect only the cookie attributes: `HttpOnly`, `SameSite=Lax`, `Path=/`, expiry, and `Secure` outside local HTTP. Do not paste or screenshot the value.

If frontend reports `502 backend_unavailable`, verify the frontend container can reach the internal backend service:

```bash
docker compose exec -T frontend node -e "fetch('http://backend:8080/api/health/ready').then(async r => console.log(r.status, await r.text()))"
```

## Port already in use

Identify the owner without killing it automatically:

```bash
ss -ltnp | grep -E ':(3000|5432|8080)\b'
```

Choose alternate `FRONTEND_PORT`, `POSTGRES_PORT`, or `BACKEND_PORT` in a local `.env`. When running the backend outside Compose, update `DATABASE_URL` to match the published PostgreSQL port.

## Migration failed

```bash
make migrate-status
docker compose logs --tail=100 postgres
```

Do not mark a failed version as applied until the database state is inspected. Goose normally wraps a SQL migration in a transaction, but a future file marked `NO TRANSACTION` can partially apply. Production recovery should usually be a reviewed forward migration.

## Testcontainers cannot connect to Docker

```bash
docker info
docker run --rm hello-world
```

The integration test intentionally needs a real Docker provider. Unit tests remain available with `cd backend && go test ./...`, but they do not replace PostgreSQL integration validation.

## sqlc generation differs in CI

Run the pinned generator and inspect the change:

```bash
make sqlc
git diff -- backend/internal/db
```

Commit valid generated output together with the query/schema change. Never hand-edit files beginning with `Code generated by sqlc`.

## Clean local database reset

This removes the named Compose volume and all local AuroraShop database data. It is destructive and cannot be recovered unless separately backed up:

```bash
docker compose down --volumes
docker compose up -d postgres
make migrate-up
```

Verify the Compose project is named `aurora-shop` and that no needed local data is present before running the first command.

## Graceful-shutdown check

With the API serving requests, stop it with SIGTERM and confirm the log contains `shutdown signal received`. The server has a ten-second drain budget. Later load tests will verify in-flight checkout behavior during termination.
